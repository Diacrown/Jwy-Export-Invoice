### Known open items

1. **Byte-match to manual workbook (highest priority).** Our generator
   writes a thinner workbook (~176 rows × 14 cols) than the real
   `EXP570 B-JEW MASTER DETAILS.xlsx` (~760 rows × 38 cols). Real file
   uses `IF`-chain indirection from a staging area (cols Q:AE) for
   buyer/consignee/bank blocks; ours writes resolved literals. Needs a
   real diff from the user to iterate against.
2. **AR base-gold-lock derivation.** UI slot exists (`df36899`) but the
   clerk still types the number. Open question from `docs/02`: is AR
   from prior-quote cost, hand-tuned for VA%, or prior-invoice
   carryover? Answer unlocks automation.
3. **Preferential-agreement rules** for NZ / UK / USA / EU — seeded
   blank; confirm with Accounts.
4. **Settings UI** — `app_settings`, `hsn_table`, `labor_rates` are
   editable only via Supabase Table Editor. In-UI admin would help.
5. **First real test invoice** not yet produced.

### Confirmed facts worth keeping

- **Gold rate `E98` / `E167` is in USD per troy ounce of pure gold**
  (not INR/gm), reconciled against EXP532 Lot 1 = \$112.54/g at 18K
  with `E98=4662.4965`. The INR/USD rate at `E114` / `E176` is applied
  separately at the C&F total line. See `src/lib/calculations.ts`
  `goldRateUsdPerGm()`.
- **Lot grouping** by `(KT, Color, JewelleryType)` matches all 9
  sample invoices; see `src/lib/grouping.ts`.
- **Remarks → HSN** mapping:
  `MINED` → 71131913, `LGD` → 71131914, `COLOR` → 71131915,
  `PLAIN` / `MOUNT` → 71131911. See `classifyJewellery()`.
- **Labour rates** in samples: ₹1,275/gm for 9K/14K/18K,
  ₹2,000/gm for 18K-PD. Seeded in `labor_rates`.
- **SDJ-JB labour rate per KT** is pulled from the vendor invoice when
  the user uploads it in the optional second slot.
- **Diamond India purchase invoice format** has NOT been shared — the
  parser doesn't yet read it; the clerk types the gold rate + purity +
  invoice number into the per-invoice form.

## Three high-value tasks to hand Claude Code (one at a time)

In order of impact:

### Task A — Byte-match one real invoice

```
Produce a byte-identical generated xlsx for one real shipment. Steps:
  1. Pick an SJ-50 file that has a matching manual EXP in the Previous
     Export Invoices Reference folder (e.g. the Oct 15 2026 batch).
  2. Run `npm run local-run <path>` to produce generated-by-ts.xlsx.
  3. Use openpyxl (via a Python helper or any xlsx library) to diff
     the generated workbook against the real one cell-by-cell.
  4. Iterate src/generators/xlsx.ts until the diff is zero on
     non-data cells (labels, formulas, formatting) and matches on data
     cells.
Consider switching to a template-fill approach: load a cleaned copy of
the sample workbook, keep the staging area (cols Q:AE) and the IF
chains intact, only overwrite data cells.
```

### Task B — Settings tab

```
Add a Settings tab for admin users (role = admin) to edit app_settings,
hsn_table, and labor_rates in-UI. Read:
  - src/storage/settings.ts for the current loader functions
  - supabase/schema.sql for the table shapes
Reuse the Dropdown component for labor-rate KT selection. Validate
values client-side before persisting. Add an audit_log row on every
change.
```

### Task C — Stones register autofill

```
When the clerk types a diamond certificate number in the Pieces grid,
look it up in the stones_register table and prefill origin,
color_clarity, and rate_usd_per_ct if the certificate is known. Debounce
the lookup. On generate, upsert the row with the latest values. Already
wired server-side in src/storage/invoices.ts; add the UI side only.
```

## What NOT to do without checking first

- Don't change `src/lib/calculations.ts` arithmetic without running
  `scripts/local-run.ts` against a sample and confirming the lot
  totals still match the expected values documented in
  `docs/01-workflow-analysis.md` §5.
- Don't rename columns in `supabase/schema.sql` without a migration —
  the live Supabase project is already populated.
- Don't add more top-level routes until the Dashboard + 5-tab flow is
  stable; the UX is intentionally a single-page flow.
- Don't switch state management to Redux / Zustand / etc. — the current
  React hooks + per-component useState is sufficient for the data
  volume and keeps new-hire onboarding simple.
